# Design review: GPT-6-Astra (2026-10-15)

> Raw report from GPT-6-Astra (via Codex CLI, high reasoning effort, read-only), translated from the original Turkish. Section numbers refer to the version of `research.md` at the time of the review; the synthesis and the fixes applied are in [research.md §14](../research.md).

## 1. Overall verdict

**In its current scope this design is not ready to become a reliable course delivery.** The biggest risk is designing an interdependent agent platform before proving one loop in which learning actually adds value. The game-plugin boundary, deterministic verification and the L0 comparison are the right choices, but the runtime contracts do not back them up. Success is possible, but the first delivery should be **a Minecraft prototype that shows the measured contribution of learning on bounded tasks**, not "a general system that plays Minecraft perfectly".

I read all four files and changed none. The external verifications below are selective; they are not a complete audit of the bibliography.

## 2. Critical problems

### 1. The safety measure is unrelated to the asset it tries to protect — §5.5, §13, decision #8

**Problem:** the inference "`node:vm` is not a security boundary → local server only" is invalid. Using a local server does not protect the developer machine and API keys from generated code.

**Evidence/risk:** Node explicitly does not treat `vm` as a security mechanism; asynchronous work can also escape the timeout under some conditions. [Node 22 docs](https://nodejs.org/docs/latest-v22.x/api/vm.html#timeout-interactions-with-asynchronous-tasks-and-promises).

**Recommendation:** run generated code in a separate execution environment without keys, with restricted file/network access and resource limits. Route game operations through a permission-checked primitive broker; keep the watchdog in an external process. A separate process alone is not a security boundary.

### 2. Who controls the bot is undefined — §6.4, §9.3

**Problem:** skills, the danger monitor and pipeline triggers all intervene in the same movement/inventory resources.

**Evidence/risk:** when night, low health and a full inventory trigger together, three different "go home" flows can race. Sending an `AbortSignal` does not guarantee that walking stops; pathfinder's normal `stop()` waits for the next node. [Pathfinder API](https://github.com/PrismarineJS/mineflayer-pathfinder#botpathfinderstop).

**Recommendation:** define a single action owner, explicit priorities, resource ownership and interrupt acknowledgement. Late results of interrupted work must not affect new work. Re-validate preconditions before "continue".

### 3. The real-time target is not budgeted mathematically — §2.4, §6.1–6.4, §11

**Problem:** one request in flight, a 5 Hz loop and 70–500 ms service latency together cannot deliver a steady 5 Hz.

**Evidence/risk:** a serial call taking 300 ms caps out at about 3.3 Hz excluding overhead. Waiting up to 200 ms for a danger scan + 300 ms of inference consumes 500 ms before the interrupt and the action even start. A retry with a second provider makes it longer.

**Recommendation:** handle emergency danger response in L0. L1 should make latency-tolerant tactical choices. Measure the chain: event occurrence → observation → decision → interrupt → the server applying the action.

### 4. A skill writes its own exam — §4.6, §8.2–8.3

**Problem:** the same induction pipeline produces the code, the intent card and the success predicate.

**Evidence/risk:** if the model misreads the "shelter" intent and produces four walls, the predicate written from the same misreading may also say success. Deterministic computation does not turn a wrong specification into a right one.

**Recommendation:** keep evaluation predicates independent of the generator and frozen in advance. Test the verifier itself with negative examples such as a missing roof, an unreachable door, an enemy inside and a pre-existing structure. Store undecidable results as `unknown`.

### 5. The contribution of "learning" cannot be separated from the starter code — §8.1, §8.4, §11

**Problem:** a general `obtain`, 15–40 primitives and about 20 ready skills may already solve most of the evaluation.

**Evidence/risk:** success on wood → diamond tasks may be the success of a hand-written planner rather than of learned skills. A drop in LLM calls may also come from the bot waiting more.

**Recommendation:** freeze the starter library. Measure transfer before/after learning on task families not included in it. The main metrics should be success, completion time and model calls per task, not only calls per hour.

### 6. "Exact packets" is confused with "exact meaning" — §4.3–4.6, §7

**Problem:** protocol events do not guarantee intent, full world knowledge or causality.

**Evidence/risk:** a placement request may fail; the player may put the table next to the tree by accident; resources may exist in unseen regions. The claim "we removed perception" hides the hard part.

**Recommendation:** keep request, server acknowledgement, observed change and inferred meaning apart. Keep the raw recording; make L1 cleaning a reversible marking. For generalizing from one demonstration, use counterexamples and different start states.

### 7. Reset and counterfactual labeling are assumed to be too easy — §6.7, §13

**Problem:** the same seed and `/give /tp /summon` commands do not produce the same experimental state.

**Evidence/risk:** world changes, dropped items, entity states and timing can differ. Trying each action once and labeling the winner teaches noise. Also, the label "took damage within three seconds?" depends on the chosen action: a correct escape can wrongly label a dangerous state as "safe".

**Recommendation:** use versioned world snapshots, state-integrity checks and repeated branches. Keep the danger label separate from the policy outcome; evaluate outcomes as distributions.

### 8. The general `obtain` is not a small helper but a planner in itself — §8.1

**Problem:** the recipe graph is not the whole resource-acquisition problem.

**Evidence/risk:** there are alternative recipes, fuel, tool durability, station access, inventory capacity and resources that cannot be found. A "produce the missing material" loop can depend on its own tool or on an unreachable raw material.

**Recommendation:** support a finite item set in the first version. Separate recipe dependencies from acquisition actions; define cycle detection, resource reservation and explicit `unsupported/unreachable` results.

### 9. API compatibility is mistaken for behavioral compatibility — §6.3, §6.5–6.6

**Problem:** the same request/response shape does not make providers' confidence values comparable.

**Evidence/risk:** Unsloth explicitly says that Unsloth, Laya and Jev compute `confidence` differently and that thresholds should not be transferred. [Unsloth serving docs](https://unsloth.ai/docs/models/decision-laya).

**Recommendation:** tie thresholds to the `(question, provider, model version, projection)` combination. "Two models agreed" is not a guarantee of correctness; measure shared errors. Do not bind the core contract to every detail of TypeSafe.

### 10. Generality is protected with the wrong metric — §5.2–5.4

**Problem:** "no game names in the core" and "zero-line changes" are not proof of architectural generality.

**Evidence/risk:** a meaninglessly generic JSON interface can also give zero changes, pushing all complexity into plugins. In a pixel environment `checkPredicate` may not be exact and `reset` may not exist.

**Recommendation:** define a small mandatory contract and optional capabilities. Measure generality by plugin development time, duplicated code, required escape hatches and behavioral parity. Do not count contract changes in the first version as failure.

### 11. Autonomy level and authority are mixed up — §5.7

**Problem:** `approver` can behave like `full` on timeout; the policy table below describes narrower behavior.

**Evidence/risk:** a user who selects "the mode that asks for approval" may find their valuables spent because they did not answer. High model confidence does not create permission.

**Recommendation:** separate communication preference from authority. A timeout must not grant new permission; skip the risky step, choose an alternative or end the task. That way the bot keeps its limits without blocking on a question.

### 12. A seed cannot be a world identity — §7.5

**Problem:** two worlds generated from the same seed become different states over time.

**Evidence/risk:** after a test reset, the chest, mine and portal memory of a previous run can carry over. That produces both wrong behavior and evaluation leakage.

**Recommendation:** use `world_instance_id`, `episode_id`, dimension and reset generation. Keep the seed as metadata only. Lessons that transfer across worlds should pass a separate generality check.

## 3. Gaps

Error handling, versioning and telemetry headings exist; what is missing is enforceable contracts:

- **State consistency:** snapshot versions, event sequence numbers, filling gaps in a broken event stream, `unknown` fields.
- **Restart:** reconciling actions known to be sent but not known to be applied; preventing duplicate effects on resend.
- **Authority separation:** the evaluator's `/give`, reset and ground-truth access must not be open to the agent.
- **Data lifecycle:** atomic publishing of SQLite and `.js` files; skill dependency hashes, migrations, provenance of recordings and labels.
- **Operations:** API outages, the PC sleeping, GPU memory pressure, log disk limits, training/serving contention.
- **Observability:** shared run/decision/action ids; queue time, discarded stale answers, interrupt latency and verifier disagreement.

## 4. Unnecessary complexity / what to cut

Remove from or postpone for the course delivery:

- Supporting a Python SDK, WebSocket and in-process loading at the same time.
- All six L1 providers and all 18 decision points.
- Fine-tuning, automatic skill merging and a learned router.
- The visual pipeline editor, scheduling, phone notifications.
- Behavior-changing mood, aesthetic surprises.
- The pixel plugin, cross-game skill transfer and a generic memory backend system.

**Backbone to keep:** the Minecraft plugin, a single task executor, L0 safety, L2 generation/repair, a small skill store, an independent verifier and an evaluation runner. Limit the recording feature to one skill family at first.

## 7. Alternative architecture and creative suggestions

**The architecture I recommend:** one TypeScript host; inside the Minecraft plugin, state projection, L0 safeguards and a single action owner; a separate isolated skill executor; an independent evaluation process. L1/L2 do not write control directly; they produce proposals. The executor applies them after checking the current state and permissions.

In addition:

1. **A bounded skill language before free code:** a small language composed of primitives narrows the execution and test surface.
2. **Shadow-mode L1:** at first it proposes decisions but does not apply them; record where it diverges from L0.
3. **Working skill + candidate version:** a repair does not overwrite the current skill; the candidate is not activated until it passes regression.
4. **Learning the difference from a demonstration:** instead of rediscovering existing primitives, extract the demonstration's new order, conditions and exceptions.
5. **Counterexample factory:** before replaying a successful demonstration, generate states that would break the skill: a missing tool, an obstacle, a changed target.
6. **Planned observation actions:** for "I don't know", opening a chest or inspecting an area should be legitimate actions; uncertainty should not turn into automatic guessing.

## 8. Critique of the evaluation plan

**The current measurements can show demo success; they do not yet prove a reliable learning claim.**

Approximate 95% Wilson intervals under an independent Bernoulli assumption:

| Result | Interval for the success rate |
|---|---|
| 8/10 | 49.0–94.3% |
| 4/5 | 37.6–96.4% |
| 23/25 | 75.0–97.8% |

If tasks differ or repeats cluster on the same seed, even these simple intervals are not enough. Three repeats are a start; they do not automatically give statistical significance.

Fixes:

- **Separate learning and evaluation:** freeze the library during testing. Measure online learning separately.
- **Paired comparison:** compare methods on the same task/start state; account for clustering at the seed/task level.
- **Choose the main hypothesis in advance:** first the contribution of the learned library, then L1. Do not open all ablations at once.
- **L1 data quality:** 200–500 consecutive states are not independent samples. Measure miss rate on rare dangers, false alarms and abstention behavior.
- **Keep failures:** do not drop timeouts, disconnects and verifier uncertainty from the report.
- **Fix the metrics:** wall-clock time, cost per task, deaths/hour, damage, time without progress, p95/p99 reaction and false success reports.
- **Fair ablations:** keep L0 safety in the "no S1" arm. Add a "structured only" arm to the memory comparison.
- **Recording generalization:** instead of jitter on the same seed, use unseen terrain, materials, orientation and missing preconditions.

Sample sizes should be computed from pilot variance and the smallest meaningful difference, not from an arbitrary "three repeats".

## 9. The first two weeks of coding: five experiments

The thresholds below are proposed engineering gates, not guarantees of scientific sufficiency.

| Experiment | Hypothesis and experiment | Success criterion | Time |
|---|---|---|---|
| **1. Execution and interrupts** | The walk/mine/craft/chest flow works with the chosen versions. Apply mid-action interrupts, disconnects and process kills. | No silent loss in 30 cycles; after the interrupt acknowledgement, stale work cannot send actions. | 2 days |
| **2. Verifier and reset** | Success can be measured independently. Build correct/incorrect final states for three tasks and 20 resets. | No false success on the prepared negatives; defined fields of the start state match. | 1.5 days |
| **3. L1 value and latency** | Jev adds value over L0 on specific contextual decisions. Compare L0/Jev/one local candidate in paired scenarios. | A practical gain on a pre-selected metric without more health loss; p95 time within the limit. Otherwise L0. | 2 days |
| **4. Learning contribution** | One new composite skill gives a gain on reuse. Compare the frozen core with core + learned skill. | Time/calls fall on unseen examples without lower success; the skill is actually called. | 2 days |
| **5. Transfer from demonstration** | Intent can be extracted from packets + narration. Produce a skill from two short demonstrations; run it at different positions/orientations and under negative conditions. | At least 8/10 transfers; no false acceptance in negative cases; the oracle is independent of the generator. | 2.5 days |
