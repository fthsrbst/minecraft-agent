# Design review: Claude Opus 5.5 (2026-10-15)

> Raw report from a Claude Opus 5.5 sub-agent (with web verification), translated from the original Turkish. Section numbers refer to the version of `research.md` at the time of the review; the synthesis and the fixes applied are in [research.md §14](../research.md).

Read: `docs/research.md` (all 1147 lines), `AGENTS.md`, `docs/notes.md`, `docs/backlog.md`. Web verifications are at the end. No project file was changed.

## 1. Overall verdict

The research part is good. The Jev/Doom correction, the reading of Voyager's source code and the idea that "location questions are solved with code, not RAG" are genuinely valuable. But as it stands, the document is **not the plan of a course project but the plan of a five-year research program**: 13 modules, 4 model layers, 6 L1 providers, a 10-method protocol, a 14-component plugin contract, a persona, a visual editor and a fine-tuning pipeline. On top of that, the delivery date is not even known (an open question in notes.md). **The single biggest risk:** the first end-to-end slice (bot → LLM code → sandbox → verification → library → a report with ≥20 tests) finishes late. None of the 14 milestones has a duration. **The biggest technical risk:** the single Node process + `node:vm` assumption. This setup does not guarantee timeouts or interrupts for async LLM code; once the event loop is blocked, the idea that "a 5 Hz monitor saves the bot" collapses too.

## 2. Critical problems (by severity)

**K1. Scope without a schedule (§12, §0, notes "Delivery date")**
- *Why it matters:* there are 14 milestones between M0 and M9, and many of their "done" criteria are research projects in themselves (M5b fine-tuning, M6 recording). A system that has not run its evaluation two weeks before delivery means zero points in the course.
- *Recommendation:* fix the delivery date first. M0–M3 + a small M7 = "the deliverable core". The rest in order if time allows.

**K2. The sandbox and interrupt model is wrongly assumed (§5.2 `runSkill`, §6.4, decision #8)**
- *Why it matters:* the `timeout` option of `node:vm` only interrupts synchronously running code. Skills are `async`, and code running after the first `await` is outside the timeout. Node's documentation says this explicitly under "Timeout interactions with asynchronous tasks and Promises". An LLM-written `while(!found){...}` locks the event loop. At that moment Mineflayer physics, keepalive, the L1 monitor and telemetry all stop, and the server kicks the bot.
- `AbortSignal` is cooperative too: if LLM code does not check the signal, nothing is interrupted. Pathfinder, dig and collectblock each have their own stop API.
- *Recommendation:* run skill code + the bot in **a separate process** (the plugin process). The core acts as a watchdog and kills and reconnects the process on a hang (~3–5 s). Remove the "TS plugins can also be loaded in-process" option. Additional measures:
  - Wrap the primitives shown to the LLM so that every call checks for aborts.
  - AST rule: loops without an `await` inside are forbidden.

**K3. L1's value as a 5 Hz danger monitor is unproven and probably negative (§2.4, §6.2 #1–3, §6.4)**
- *Evidence:*
  - Jev's own "jaggedness" page says it is weak with numbers, arithmetic, dates/times and numeric representations. Danger is a numeric decision (distance, health, enemy type).
  - In `jev-plays-doom` the "intent" criterion scored −0.60. The model worked only when the threshold was written in the prompt, i.e. we are giving the rule to the model. Episode variance (4–5 kills) is larger than the measured differences.
  - 212 ms is a single average with no p95, and network latency comes on top. Meanwhile a Minecraft tick is 50 ms and a creeper fuse is 1.5 s.
  - In Ronak Malde's run, 131 Jev calls / 523 s ≈ **0.25 Hz**, event-driven. That run does not validate a 5 Hz monitor.
- *Recommendation:* make danger, mode and escape L0 (rules + timers + the pvp plugin). Move L1 to **language-semantic** points: command → skill (#6), narration sentence type (#12), skill reranking (#5), stagnation detection (#4). Make calls event-driven. The value test (#10d) already says this; apply it now instead of discovering it later.

**K4. The evaluation does not measure the "learning agent" claim (§8.4, §11)**
- *Why it matters:* a hand-written `obtain(item,n)` solver + ~20 core skills solve much of the tech tree **in code**. "Diamond pickaxe ≥8/10" then measures a hand-written bot, not learning.
- Also, the library seems to be learned on the same 10 seeds it is tested on. That is train/test leakage.
- *Recommendation:*
  - Separate learning and test seeds.
  - Report "given" (hand-written) and "learned" skills separately.
  - Make the main claim "the library reduces L2 calls and time in **unseen** seeds".
  - Freeze the task set before learning starts.

**K5. No statistical power (§11, ablations)**
- *Evidence:*
  - The 95% Wilson interval of 8/10 success is **[0.49, 0.94]**, of 4/5 **[0.38, 0.96]**.
  - "At least 3 repeats per arm" cannot separate arms on a binary success measure.
  - "≤1 death in 3 days on normal" looks like a single run.
  - "LLM calls per hour fall monotonically" cannot be tested on a noisy series.
- *Recommendation:* ≥20–30 paired runs (same seed, same task) in the main arms. Use McNemar tests and bootstrap confidence intervals. Report a slope ± CI instead of monotonicity. Fewer ablations, more repeats.

**K6. No wall-clock or compute budget (§11, §12)**
- *Estimate:* one diamond run ≈ 60 iterations × (L2 10–60 s + minutes of in-game execution) ≈ 1–2 hours. 6 ablations × 10 seeds × 3 repeats = 180 runs ≈ **180–360 hours**, with no parallelism.
- *Recommendation:*
  - Produce an evaluation budget table: time per run, $, number of parallel servers. N Docker servers + bots on the PC.
  - Keep long-horizon runs few. Put the weight on 2–10 minute scenario tasks (start states set up via RCON).

**K7. The Haiku→Sonnet cascade contradicts the "budget is not a constraint" decision (§6.8, decisions #5/#5b)**
- *Reasoning:* the cascade's only justification is cost and speed. If budget is not a constraint, only speed remains. But in the worst case the cascade adds both models' latency (the document admits this), and since the prompt cache is per model, cache reuse is lost.
- Prices (Anthropic model table, 2026-10): Haiku 5.5 $0.10/$0.50, Sonnet 5.5 $2/$10, **Opus 5.5 $4/$20**. Opus is only 2× Sonnet. The justification for "no Opus for hard repairs" is weak.
- *Recommendation:*
  - Start with one model for code writing and repair (Sonnet 5.5, with effort tuned). Give Haiku the high-volume work: summaries, diary, skill descriptions.
  - Keep the cascade as an **experimental arm**, not an architectural requirement.
  - Measure Opus 5.5 as a candidate for 3rd+ repairs and skill induction.

**K8. The plugin protocol is a premature abstraction (§5.2–5.4, decisions #9, #12)**
- *Why it matters:* 10 methods and 14 components are derived from a single game. The second game is in M9, i.e. after delivery. So "core change ≈ 0" **cannot be measured** at delivery, and the target in §11 is left hanging. Two execution paths (in-process + JSON-RPC) also double the testing load. `knowledge`, `scenario`, `record`, `memoryExtractors` and the "persona flavor" are speculative contracts.
- *Recommendation:* keep the process boundary (needed for K2), but make the protocol thin: `observe / act / runSkill / interrupt / reset / events`. Keep the rest as TS interfaces inside the Minecraft plugin. Test the contract not on paper but with a **one-day ViZDoom spike** (Python, observe/act only).

**K9. No perception-fairness / "x-ray" policy (§7.2, §7.3, §8.1)**
- *Why it matters:* Mineflayer knows all loaded chunks: `findBlocks` also finds diamond ore inside stone. The "resource ledger / exhaustion estimate" then becomes an exact calculation, and "reaching diamond" becomes easier. Voyager only partly limited this with `maxDistance 32` ("Do not cheat").
- Also, unrestricted LLM code can call `bot.chat('/give …')`. If the bot is op, the evaluation becomes invalid.
- *Recommendation:*
  - Write the visibility model as a DECISION: only blocks exposed to air, or raycasting.
  - The agent's bot must not be op. Scenario setup only via RCON.
  - Statically forbid `bot.chat('/…')` in LLM code.

**K10. The dependency ecosystem is stale (decision #2, §5.5)**
- *Evidence (npm, 2026-10-15):*
  - `mineflayer-pathfinder` 2.4.5 (2023-09), `mineflayer-pvp` 1.3.2 (2022-07), `mineflayer-tool` 1.2.0 (2022-05).
  - `prismarine-viewer` npm 1.33.0 (2025-02). The `supportedVersions` list on master ends at 1.21.4 and 26.1, so 1.21.11 falls back to 1.21.4 assets.
  - Mineflayer 4.39.0 itself tests 1.21.11 and 26.1.
- *Recommendation:* run a compatibility spike in M0 (see §9 E1). If needed, copy the versions or forks Mindcraft uses. Budget your own pathfinder patch from the start.

**K11. The two hard parts of record a skill are underestimated (§4.5, §4.6, decisions #11/#11c)**
- *(a) Proxy:* the 1.20.2+ "configuration" phase, signed chat (requires `enforce-secure-profile=false`), compression. Crafting arrives through two separate paths: the recipe-book `place_recipe` packet and slot clicks. The client's intent packet and the server's acknowledgement can diverge.
- *(b) Generalization:* producing parameterized, tested code from 1–3 demonstrations is the hardest research problem in this document. The "≥4/5" target has no justification.
- *Recommendation:* make v1 two parts:
  - A **blueprint** from the server-side block diff + `buildBlueprint` (deterministic, no LLM, a very good demo).
  - A named subgoal macro.

  The LLM only writes the intent card. Behavioral skills (farming, combat) go to v2.

**K12. Counterfactual labeling is expensive and noisy (§6.7)**
- *Why it matters:* Minecraft is not deterministic (mob AI, spawn RNG, tick timing). The same `/summon` gives different results. So each option needs many rollouts, and the game runs in real time.
- *Recommendation:* rely on hindsight labels ("damage within 3 s") and rule oracles. Try counterfactuals only as a pilot on one decision point.

## 3. Gaps

- **Error handling/recovery:** disconnects, server crashes, unloaded chunks, death in the middle of a skill, skill idempotency. §9.3 covers this only for pipelines.
- **Concurrency:** synchronous `findBlocks` and pathfinder computation block the event loop. The state may have changed by the time an L2 answer arrives; freshness checks exist only for L1 (§6.3).
- **State synchronization:** snapshots or an event stream between core and plugin? Versioned state and ordering guarantees are undefined.
- **Test infrastructure:** no fake bot for primitive unit tests. Docker MC in CI, a deterministic test world and a time-boxed scenario runner are undefined.
- **Observability:** telemetry is only tokens/$/ms. No trace id (L2 call → skill → primitive → event), session replay or error clustering.
- **Version matrix:** skill ↔ primitive API ↔ prompt ↔ model ↔ MC version. The practical side of skill drift (§1.5).
- **Security:** what is given to the vm context (`require`, `process`, `fetch`, `.env`) is unspecified. Chat, sign and book text is a prompt-injection channel to L1 and L2 (Jev's page also admits that state can be adversarial). The bot's op permission is an open issue (K9).
- **Data management:** 5 Hz × 2k tokens of logs ≈ 36M tokens/hour of text. Retention, compression and dataset versioning are undefined.
- **Machine dependency:** embeddings, Whisper and the local L1 are on the PC. When the PC is off, the Mac side does not work; there is no fallback.
- **Course mapping:** the "≥20 tests, success rate, cost, latency" and "3–5 minute video" outputs are not mapped to milestones. There is no deterministic "filming seed" plan for the demo.

## 7. Alternative architecture and creative suggestions

1. **Build on Mindcraft.** The Mineflayer integration, multi-provider support, command + code modes and 1.21.11 support are ready. M0–M2 would shrink from weeks to days. Your contribution comes on top: a contracted skill library, deterministic verification, recording. (Check its license and code quality.)
2. **Have skills written in TypeScript and check them with `tsc`.** Primitives the LLM invents and wrong arguments are caught at compile time. This is the cheapest objective form of a Haiku→Sonnet trigger.
3. **Task IR / behavior tree as the skill format first.** The LLM produces a bounded DSL instead of free JS; free code is used only in leaf nodes the DSL cannot express. Most sandbox, interrupt, resume and static-verification problems resolve themselves.
4. **Test-first skill synthesis (TDD).** L2 first writes the postcondition predicate and the scenario setup (RCON `/fill /give /tp`), then the code. The verifier is code. It removes Voyager's weakness "an LLM decides success" at the root.
5. **Frozen scenarios with `/tick freeze` and `/tick step` (1.20.3+).** Measure L1/L2 decisions while the game is paused; separate latency from quality. Build the danger dataset deterministically. (Risk: Mineflayer physics is client-side; spike first.)
6. **An offline decision benchmark.** Extract `(state, decision, outcome)` tuples from game logs; compare L1 providers in seconds without running the game. Run in-game A/B only for finalists.
7. **Teaching by correction (DAgger style).** Instead of generalizing from one demonstration, the bot tries and the human corrects with `//` ("no, place the torch first"). The correction becomes a rule in the skill. Labeling cost is much lower and the demo is more impressive.
8. **A night shift (L3) with the Batch API.** Skill descriptions, regression repair proposals and teacher labels run in bulk at night via Message Batches (50% discount), keeping load off the real-time path.

## 8. Critique of the evaluation plan

- **Weak claim–measurement match:** see K4 (solver confound, seed leakage), K5 (power), K6 (time).
- **Missing metrics:**
  - Wall-clock duration, $ per success and L2 p95 latency.
  - Crash/disconnect rate and unattended run time (MTBF).
  - Skill reuse rate, library size–success curve.
  - The share of "dead" (never-called) skills and the success of learned skills on holdout seeds.
- **L1 "must beat it statistically":** the test is undefined. Use McNemar on paired decisions + in-game hindsight outcomes. ECE is not enough for calibration; report precision and recall at the selection threshold.
- **"Claude vs local model" L2 ablation:** the MindForge finding in the document (7–8B models struggle with basic tasks) already predicts the result. A wasted run; cut it.
- **Skills from recordings ≥4/5:** the unit should not be "demonstration" but "demonstration × N fresh-world replays". The report should give a success rate per demonstration ± CI.
- **Autonomy "questions = 0":** true by construction, not a measurement. What should be measured is the number of wrong assumptions in `full` mode and the number of later corrections by the user.
- **Pre-registration:** freeze the task set, seeds and success predicates before evaluation starts. Tune prompts only on development seeds.

## 10. Questions for Fatih

1. **What is the delivery date and how many hours per week can you work?** Every scope decision depends on it.
2. **Which is the report's main claim:** a "learning agent" (the library speeds things up in unseen worlds) or a "bot that plays well" (including the hand-written `obtain` solver)? They need different evaluations.
3. **Perception fairness:** can the bot see inside stone (x-ray), and are game commands and op permission forbidden? "Playing perfectly" only makes sense once this is decided.
4. **If budget is not a constraint**, why is Opus 5.5 left out and why is the Haiku-first cascade mandatory in the first version? Is the goal latency, or showing "cost optimization" in the report?
5. **What is the minimum target for the record-a-skill demo?** Is building (a blueprint) enough, or is a behavioral skill (farming, combat) required? And will recording happen on the Mac or the PC?
